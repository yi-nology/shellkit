## 批次 0：确定性修复（半天，改动最小、收益最大）

> 这批的目标：把「崩溃」「静默越界」变成「明确的非 0 退出码 + 人话错误」。

### 0.1 修 `__cmds_csv` 未初始化，并把失败路径改成受控的

- **改哪里**：`shellkit` 的 `cmd_upgrade`
- **怎么改**：
  1. 读完清单立刻 `__cmds_csv="$SK_MANIFEST_COMMANDS"`（或把声明改成带默认值）
  2. 写盘失败分支改成：先清临时目录 → 再用**已推进的基线**落盘 → 再 `return "$SK_ERR"`
  3. 临时目录改用 `trap` 兜底清（注意 bash 3.2 的 trap 语义差异，见 AGENTS.md 第 1 条坑），
     不要指望每条 return 路径都记得清
- **验收**：
  - 注入 `cp` 失败 ⇒ 退出码 1，stderr **不含** `unbound variable`，含一句人能看懂的话
  - `$TMPDIR` 里不留 `shellkit-upgrade.*`（实测每次失败泄漏一个工程模板全量副本）
  - 清单里的基线与磁盘上的文件**一致**（已成功的推进了，没成功的没推进）
  - 恢复写权限后再升一次 ⇒ 被跳过的文件仍然「left alone」，模板改动仍然能升进去

### 0.2 清单里的项目名必须合法

- **改哪里**：`cmd_upgrade` 读出 `SK_MANIFEST_NAME` 之后
- **怎么改**：跑现成的 `_sk_valid_name`（`shellkit:292`）；不合法就
  `log_error` + `return "$SK_VERIFY"`（退出码 5）
- **注意**：`cmd_new` 已经在用同一个校验（`shellkit:472`），所以**不新增函数**，
  只是把 upgrade 补齐
- **验收**：`name=../../x` / `name=.` / `name=带空格` ⇒ 全部拒绝、非 0 退出码、
  **一个文件都不写**（含工程外）

### 0.3 目标路径必须落在工程目录内

- **改哪里**：同上，构造 `$__dir/$__rel` 之后、任何写操作之前
- **怎么改**：把目标路径规范化成绝对路径（`cd` + `pwd -P`，或逐段比较前缀），
  不在 `$__dir` 之内就拒绝；顺带检查 `$__dir` 本身、中间目录是不是符号链接
- **验收**：构造 `name=../../X` ⇒ 拒绝；工程内正常路径不受影响（回归全绿）

## 批次 1：写盘原子化 + 升级事务化（1~2 天）

### 1.1 写文件一律走原子写

- **为什么**：库里已经有「临时文件 + rename」，一次性解决三件事：
  ① 写盘被打断 ⇒ 目标仍是旧内容（完整），不再是 0 字节空文件
  ② 不再跟随符号链接写穿（rename 替换的是链接本身）
  ③ 模板渲染的落盘也能统一
- **怎么做**：升级路径里的 `cp -f` 换成原子写；保留 `chmod` 语义
  （原子写默认 644，bin 要 755）
- **落地时的修正**：库里新增的是 `fs_atomic_copy`（搬文件，逐字节一致），
  不是 `fs_atomic_write` —— 后者吃的是「内容」，命令替换会吃掉文件末尾的换行，
  搬模板文件会变形。符号链接的处置也改了：批次 0 已决定「目标是符号链接就**跳过并提示**」
  （`--force` 也不写穿），比本节原先写的「覆盖链接本身」更保守 ——
  用户的软链是刻意摆的，不替他拆掉。
- **验收**：
  - `cp` 替身模拟「写一半被杀」⇒ 目标文件要么是完整旧内容、要么是完整新内容，**不出现半截**
  - 悬空符号链接 ⇒ **不再**在工程外创建文件
  - 目标是符号链接 ⇒ 跳过并提示，工程外的文件不动

### 1.2 升级事务化：候选 → 校验 → 切换 → 落清单 → 清理 ✅ 已落地

- **落地形态**：
  1. 把新模板渲染到候选目录 ✔
  2. **校验前置**：所有目标先判完、校验完（**一个文件都不动**）—— 目标是目录、
     父路径建不出来、目录不可写 ⇒ 报错退出 5，工程一个字节都不改 ✔
  3. **切换**：逐个原子替换（批次 1.1 的 `fs_atomic_copy`）✔
  4. **落清单**：最后写，清单本身走原子写；vendor 同步失败也照样落盘 ✔
  5. **清理**：候选目录、临时目录，失败路径也清 ✔
  6. **vendor 目录整体换**：先铺 `vendor/.shellkit-new` 再整体换上去；中途失败旧副本完好 ✔
- **两处与原来的设想不同**：
  - 原设想写「所有文件要么全是旧版、要么全是新版」。**跨文件做不到原子**：
    多个文件不是一次换上去的，也不做回滚（回滚会把用户的新改动一起 revert，风险大于收益）。
    能保证的是「每个文件要么是完整旧内容、要么是完整新内容」+「清单与磁盘始终一致」。
  - 符号链接**不算致命问题**（批次 0 的决定）：目标是软链就跳过并提示，
    不因为一个软链就挡住整个升级 —— 用户的软链是刻意摆的。
- **验收**：`tests/test_upgrade_txn.sh` —— 五个阶段各注入一次失败
  （目标是目录、父路径是文件、写失败、清单写失败、vendor 同步失败），
  逐条断言工程状态。对着旧代码验过会红（旧代码在「目标是目录」这一条上直接退出 0，
  把文件塞进了目录里）。

## 批次 2：把测试改真（1 天，这一批决定后面几批有没有意义）

### 2.1 引入测试钩子，让故障注入确定化

- **想法**：在升级流程的关键节点留一个**只在测试时生效**的钩子，例如
  `SHELLKIT_TEST_PAUSE=<阶段>`：命中就打印一行阶段标记并等待一个信号文件出现。
  阶段建议：`after-render` / `before-write` / `after-write` / `before-manifest` / `after-vendor`
- **约束**：钩子**默认关闭、不引入生产依赖**，只在 `SHELLKIT_TEST_HOOK=1` 时激活
- **验收**：测试能在任一阶段精确停住，然后注入 SIGTERM / 写失败 / 磁盘满

### 2.2 修掉两条「假绿」用例

| 用例 | 现在的问题 | 改成 |
|---|---|---|
| 「写不进去」 | 只断言退出码非 0 ⇒ 被崩溃蒙混过关 | 断言 stderr **不含** `unbound variable`、**含**预期错误文案、临时目录已清、清单与磁盘一致 |
| 「中途被杀」 | SIGINT 送不到后台进程 ⇒ 整条是空转 | 改用 **SIGTERM**（实测可达），并用 2.1 的钩子保证杀在**写盘阶段**；断言清单与文件一致 |

- **自检**：改完把修复临时回退 ⇒ 新用例必须变红（否则用例本身没判据能力）

### 2.3 runner 的失败原因要分类，超时上限要抬

- 「超时」和「断言失败」现在都印成同一句 `FAILED: <file>` ⇒ 分成两种失败行
- 每文件上限从 120s 抬到 **300s**：`test_ai_docs.sh` 本机就要 ~60 秒，贴着上限跑是定时炸弹
- **更根本的修法**：把 `test_ai_docs.sh` 里「把 6 个目录拷到隔离副本」那段做缓存/裁剪，
  让它稳定在 10 秒级
- **`test_http.sh` 那条不是 flaky，是 HEAD 上的真 bug**（已被并行会话修掉）：
  HEAD 的 jq-less 兜底是「一行 JSON 上 grep + 贪婪 sed」⇒ GitHub 那种一行装着好几个资产的
  JSON 会抓到**最后一个** URL（要 x86_64 却给 arm64）。并行会话已改成「按逗号拆条 +
  只取第一条匹配」，并补了「强制藏掉 jq/python3」的回归用例（对着旧代码会红）。
  ⚠️ 我先前把它记成「负载下的 flaky」是**判断错了** —— 修好之后连跑 3 次全过，
  失败只出现在修复落地之前的那次全量跑里。
- **还有一条 TTY 用例是 flaky 的**：`test_prompt_tty.sh` 的「ask_choice 用用户输入的那个答案，
  不是默认值」在同一棵树上连跑三次会「过、红、过」；对着旧代码（HEAD）单跑是过的。
  症状是读到空串（用户输入没赶上就被默认值顶掉）⇒ pty 交互有时序假设，
  负载高时更容易复现。修法：要么等输入真的到达再断言，要么改成不依赖时序的同步点。

### 2.4 补一条**元测试**：门禁自己也要被测

- 加一条用例：故意在临时副本里制造上面 8 条缺陷中的任意一条 ⇒ 对应门禁必须报红。
  现状是「缺陷 1 存在而门禁全绿」—— 说明门禁缺少自检能力

## 批次 3：日志安全接口（P2，可与批次 2 并行）✅ 已落地

### 3.1 补齐脱敏形态

- 头名：任何以 `Key` / `Token` / `Secret` / `Password` 结尾的头，
  外加 `Cookie:` / `Proxy-Authorization:` / `Set-Cookie:`
- 选项 + 值形态：`-u` / `--user` / `--password` / `--token`（短选项也要认）
- `--data 'password=xxx'` 这种「值里带敏感键名」的形态

### 3.2 显式声明机制（评审说的「安全日志接口」）

- 形态一：`run --secret-arg 2 -- cmd ...`（第 2 个参数必脱敏）
- 形态二：环境变量 `SHELLKIT_SECRET_ARGS="2,3"`
- 形态三：`run --redact-value 'my-pass'`（按**值**脱敏，适合令牌夹在参数中间的情况）
- **为什么要显式**：启发式永远漏（评估 §1.5 的表就是证据）。显式接口把「我保证它敏感」
  交给调用方，启发式只做兜底
- **落地时定的两件事**（原设想没写）：
  - 序号**命令名不算**：`run --secret-arg 1 -- false SECRET` 遮的是 SECRET（false 是命令名，
    排在第 0 位）。「第 2 个参数」说的是命令的参数。
  - `run` 顺带支持了 `--` 分隔符 —— 原来 `run -- foo` 会把 `--` 当命令去执行。

### 3.3 反向用例

- 加用例保证**不该脱敏的别脱敏**（比如 `--verbose`、`--count`、普通 `id`）
  —— 过度脱敏会让日志失去排障价值，这也是一种回归

### 批次 4 的落地记录（2026-11-11）

**4.1 提速**（`f67d6f4` + `de61601`，随 0.12.1 发布）：

- `scaffold_render` 的替换规则直接交给 `sed -e`（不再为每个文件建一个 sed 脚本临时文件），
  转义改成出参形式（零 fork）；`os_sha256` / `os_md5` 不再接 `| awk` 管道。
- 本机实测：`new` 3.74 秒 → 0.69 秒，`upgrade --check` 3.77 秒 → 0.57 秒（绝对值随机器而变）。
- 「行为不变」是硬验证出来的，不是口头保证：改前改后各生成一个工程，
  **用户自己的文件逐字节相同**，`upgrade --check` 输出逐字一致。
  `os_sha256` 的输出也钉死成「成功是摘要 + 一个换行，读不到时 stdout 全空、退出码 0」。

**4.2 流水线**（本轮）：

- `test` 矩阵加 `ubuntu-24.04-arm` —— 原生 ARM64 Linux 跑整套门禁
  （公共仓库免费提供，标签是 GitHub 官方文档里的 `ubuntu-24.04-arm`）。
- `compat` 矩阵加欧拉容器（`openeuler/openeuler:24.03-lts`，官方镜像同时有 amd64 与 arm64 变体），
  其中一份跑在 ARM64 runner 上 ⇒ **「国产系统 × ARM64」这条线有了真机覆盖**，
  而不是拿 Rocky 当近似。
- 三个下载器（curl / wget / python3）都没有时，按发行版补装一个 —— 极简镜像常常一个都不带。
- **麒麟的真实机器 CI 覆盖不了**：官方镜像在 `docker.kylinos.cn`（要鉴权），CI 拉不动。
  麒麟的**发行版识别**已有人造 os-release 用例覆盖（服务器版 RHEL 系 / 桌面版 Ubuntu 系 /
  没有 ID_LIKE 三种），其余靠手工验证 —— 这条边界写在 MIGRATING 与本记录里，别当成了全覆盖。
  ⚠️ 别把 Docker Hub 上的 `openeuler/kylin` 当成银河麒麟：读它的镜像 config 就知道，
  底包是 `openEuler-docker-rootfs`，装的是 **Apache Kylin 那个大数据 OLAP**（还带
  Hadoop / Hive / Spark），与银河麒麟 OS 无关。拿它当麒麟覆盖是认错了东西。

## 5. 门禁与提交纪律
