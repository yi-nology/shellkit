## 0. 结论摘要

| # | 缺陷 | 评审提到 | 我给的定级 | 实际后果 |

## 1. 评审提到的，我复核的结果

### 1.1 写盘失败分支上的 unbound variable —— 确认，且有连带损伤（P0）

评审说：`cmd_upgrade` 的 `__cmds_csv` 在失败分支被引用，但只在正常收尾时才赋值，
`set -euo pipefail` 下会报 `unbound variable`。**属实。**

源码依据（`shellkit:604` 声明、`shellkit:836` 赋值、`shellkit:818` 使用）：

- 声明：`local __name __rel __old __cur __new __tmp __cmds_csv __vdir`（只声明，没赋值）
- 使用：`_sk_upgrade_save_manifest "$__dir" "$__name" "$__cmds_csv" ...` ← 在「写盘失败」分支
- 赋值：`__cmds_csv="$SK_MANIFEST_COMMANDS"` ← 在正常收尾、vendor 同步之后

复现（`verify-0.12.sh cmds-csv`，用 `cp` 替身让写 AGENTS.md 失败）：

    cp: injected failure
    /Users/zhangyi/shellkit/shellkit: line 818: __cmds_csv: unbound variable

**评审没说的三处连带损伤**（都比崩溃本身更值得修）：

1. **`|| true` 救不了它。** 未绑定变量的展开错误不是命令失败，是 shell 致命错误，
   直接终止进程 —— 所以「先把基线落盘再报错」这个修复逻辑在真正需要时**一次都没执行过**。
2. **临时目录泄漏。** 崩溃发生在 `rm -rf "$__tmp"` 之前，每次失败的升级都会在
   `$TMPDIR`（macOS 上是 `/var/folders/…/T/`，不是 `/tmp`）留下**一整份渲染出来的工程副本**。
   实测：一次失败升级前后，`$TMPDIR` 里的 `shellkit-upgrade.*` 从 26 个变成 27 个，
   新增的那个目录里有 bin / lib / tests / README.md / AGENTS.md / Makefile —— 即工程模板的全量副本。
3. **不是受控错误路径。** 设计意图是「写失败 ⇒ 存清单 ⇒ 报错退出（SK_ERR=1）」；
   实际是「shell 崩溃 ⇒ 退出码 1」。退出码碰巧一样，所以没人发现；但 stderr 是
   `unbound variable`，用户完全看不懂发生了什么。

### 1.2 清单名称未校验 → 路径穿越 —— 确认，定级偏低（P0 / 安全）

评审说：清单里的项目名只检查了「非空」，拼进 `bin/<name>` 后可能落到工程目录之外。**属实，
而且比评审描述的更严重。**

链路：`scaffold_manifest_read` 只做 `name=` 取值、不做任何校验（`lib/core/scaffold.sh:330`）→
`cmd_upgrade` 只判空（`shellkit:679`）→ `_sk_new_owned_list` 把它拼成 `bin/<name>`
（`shellkit:139`）→ 渲染与复制都按这个相对路径落盘。

复现（`verify-0.12.sh traversal`，伪造清单 `name=../../OUTSIDE`）：

- 退出码 **0**，全程无告警，日志里还把 `bin/../../OUTSIDE` 原样打出来（信息泄漏 + 误导）
- 工程外的文件**被创建/覆盖**
- 再加一条伪造基线 `@file bin/../../OUTSIDE <hash>`，就能**直接覆盖工程外的既有文件**，
  内容换成模板内容 —— 复现实测：`ORIGINAL CONTENT` 被模板正文替换

危害面：任何带着 `.shellkit-manifest` 的目录（clone 下来的仓库、CI 里 checkout 出来的工程）
被 `shellkit upgrade .` 跑一次，就可能在工程外落文件。**这正是评审建议的 P0「Manifest 路径安全」。**

### 1.3 非原子写 —— 确认（P1）

评审说：cp -f` 逐个覆盖，中断可能留下不完整内容。**属实，实测更直白：**

    cp 一个 200MB 文件，写到一半 kill -9  ⇒  目标文件大小: 0 字节

也就是说中断留下的不是「旧内容」也不是「新内容」，而是**空文件**。
库里本来就有 `fs_atomic_write`（临时文件 + rename），升级路径没用它。

### 1.4 升级不是事务 —— 确认（P1）

评审说的「先删后拷的 vendor 同步」「部分模板已更新但清单没同步」在源码里属实。
这一条是设计缺口，不是一行两行能修完的，放到 v0.12.0 的批次 1 单独做。

### 1.5 日志脱敏漏网 —— 确认，且漏的面比评审列的更宽（P2）

评审点出了 `X-API-Key:` 和 `curl -u user:pass`。实测确认，而且**同一个家族的头全都漏**：

| 形态 | 结果 |
|---|---|
| `--api-key sekret` | 已遮住 ✅ |
| `API_TOKEN=sekret` | 已遮住 ✅ |
| `Authorization: Bearer x` | 已遮住 ✅ |
| `X-API-Key: v` | **明文进日志** ❌ |
| `X-Auth-Token: v` | **明文进日志** ❌ |
| `curl -u user:pass` | **明文进日志** ❌ |

根因是 `_sk_run_redact_args` 只认 `Authorization:` 一个头名（`lib/core/run.sh:69`），
且 `-u` 这种「选项 + 值」形态没有对应的敏感键名兜底。

### 1.6 评审说「已经修好」的三处 —— 我复核确认确实修好了

这三处**不要在 v0.12.0 里再动**：

1. **dotenv 写回一致**：`export OTHER=keepme` 经 `conf_set` 后仍保留 `export` 前缀，
   `conf_unset` 能删掉 `PLAIN=plain`，取值与写回用的是同一套解析规则。属实。
2. **`run_concurrent` 的失败判定**：4 个实例全失败时输出
   `concurrent instances failed: 0/4 succeeded, first failure exit 1`，退出码 1。属实。
3. **用户修改保护的三连升级**：`tests/test_upgrade.sh` 里「连升三次、基线不前进」的用例扎实，
   P0 的原始缺陷（第一次跳过、第二次覆盖）确实修好了。

## 2. 评审没提到，我挖出来的

### 2.1 升级写文件时跟随符号链接 —— 写穿到工程外（P0 / 安全）

`cp -f` 会跟随**目标**符号链接写穿。升级把模板内容写进 `$__dir/$__rel` 时，
如果该路径是符号链接，内容就落到链接指向的地方去了。两条变体都实测成立：

- **悬空符号链接**（不需要 `--force`）：`.shellkit-manifest` 说文件存在，
  但 `[ -f ]` 对悬空链接返回假 ⇒ 走「补文件」分支 ⇒ 在**工程外创建**了文件。
  复现：`README.md -> <工程外路径>`，升级后 `<工程外路径>` 出现了模板内容。
- **既有符号链接 + `--force`**：`.shellkit-manifest` 里的基线对上 ⇒ 走「更新」分支 ⇒
  **覆盖了工程外的既有文件**，工程里的链接原样保留、看不出任何异常。

两条都是**退出码 0、静默**。

这条评审只在「建议」里提了一句「拒绝可能导致越界写入的符号链接」，没有意识到它**不需要恶意清单**
就能触发 —— clone 一个仓库就带着这条路径。

### 2.2 现有「写不进去」故障注入用例，是被崩溃蒙混过关的（P1 / 测试债）

`tests/test_upgrade.sh:109` 那条「目录不可写 ⇒ 升级必须失败」的用例，断言只有两条：
「退出码非 0」+「本地修改还在」。

而缺陷 1 的表现恰好就是：升级在写盘失败时**因为 `unbound variable` 崩溃**，退出码非 0，
本地修改也还在。⇒ **这条用例是「因为 bug 才绿」的**，它对缺陷 1 完全不敏感。
实测这条用例的 stderr 里就是那行 `line 818: __cmds_csv: unbound variable`。

换句话说：缺陷 1 能一直存在而门禁全绿，正是因为这条用例只看「非 0」，不看「错得对不对」。

### 2.3 现有「中途被杀」用例完全空转（P1 / 测试债）

评审说这条用例「允许升级已经执行完成，证明不了中断安全」——**比这更糟：它根本没杀到。**

POSIX 规定：非交互 shell 里**后台启动**的进程，SIGINT 与 SIGQUIT 继承为忽略。
测试里那句：

    "$TEST_ROOT/shellkit" upgrade "$p6" --template "$tpl" >/dev/null 2>&1 &
    pid=$!
    sleep 0.2
    kill -INT "$pid" 2>/dev/null || true

`kill -INT` 打在一个**忽略 SIGINT** 的进程上 ⇒ 空操作。实测：把延迟设成 0.05s / 0.3s /
1.0s / 2.0s 四档，升级**每一次都完整跑完**并打印 `upgrade finished`。
（同一实验里 SIGTERM 能正常送达并触发 trap —— 所以修法是改用 SIGTERM，而不是改 sleep 时长。）

这条用例现在验证的是「升级跑完之后的样子」，却顶着「中途被杀」的名字。

### 2.4 本地 `make check` 是红的，CI 是绿的（P1 / 工程体验）

在干净工作树上跑 `make check`，红灯是 `test_ai_docs.sh`，但**没有任何 FAIL 行** ——
按本仓库的 runner 语义，那是**被每文件 120 秒上限杀掉**（退出码 124），不是断言失败。
单独跑同一个文件、放宽到 600 秒 ⇒ 通过，耗时约 **60 秒**。

也就是说：这条用例在本机贴着上限（120s），在整轮 `make check` 里（前面用例刚跑完、磁盘缓存状态不同）
就超了。CI 机器更快所以绿。**开发者本地会看到一条假红，且看不到任何原因。**

顺带一条改进项：runner 现在把「超时」和「断言失败」都印成同一句 `FAILED: <file>`，
应该分成两种失败行，否则每次都得手工重跑才能定位。

## 3. 顺带量到的数字

| 观察 | 实测 |
|---|---|
| `shellkit new`（生成一个工程） | ~8 秒 |
| `shellkit upgrade --check`（不落盘、不 vendor 同步） | ~5.8 秒 |
| `shellkit upgrade`（完整） | ~4.9 秒 |
| 加载一次 bootstrap | ~314ms |
| 单次 `scaffold_render`（2.8KB 文件） | 70~190ms |
| 单次 `os_sha256`（2.8KB 文件） | ~96ms |
| 写盘失败一次泄漏的临时目录 | `$TMPDIR/shellkit-upgrade.*` **+1 个**（里面是工程模板的全量副本）；实测 26 → 27 |
| `test_ai_docs.sh` 单跑耗时 | ~60 秒（上限 120 秒） |

（计时用 `EPOCHREALTIME`，避免把 `date` 自身的 fork 算进去；PATH 已摘掉回收站 shim。）

**升级慢的根因不是 vendor 同步，是「一次小操作一次 fork」。**
`upgrade --check`（既不落盘也不做 vendor 同步）就已经要 ~5.8 秒，说明时间全花在
「渲染 + 算指纹」这一段；而这段里：

- `os_sha256` 一次 ~96ms —— 算一个 2.8KB 文件的 sha256 不该这么慢，代价全在
  「起外部工具 + 再起一个管道」上；
- `scaffold_render` 每个模板变量都要一次命令替换
  （`__esc=$(_sk_sed_repl_escape "$__value")`）来 fork 一个子 shell。

⚠️ 本机 fork 成本异常高（单次 fork ~80ms，普通机器约 3~5ms），所以**绝对数字别照抄**；
但「热路径上一次操作一次 fork」这件事在任何机器上都值得改：`os_sha256` 改成一次调用
不接管道、`_sk_sed_repl_escape` 改成出参形式，能把这部分开销降一个数量级。

（旁证：另一个会话正在改的 `lib/core/trap.sh` 也在做同一类优化 ——
把 4 个信号各读一遍变成只读一遍，临时文件从 8 次 rm 降到 1 次。
「启动一次脚本要付几秒」在本机是系统性问题，不是单点问题。）

## 4. 复核的局限（说清楚哪些没验）

- 没有做独立的安全审计，也没有第三方压测；结论来自源码阅读 + 上述复现。
- 没有覆盖「清单里 `commands=` 写回时夹带换行 ⇒ 伪造清单行」这条注入路径：
  清单是逐行读的，读进来的值不带换行，所以**当前**写不进去；但写回路径没有做同样约束，
  属于「今天不可达、但少一道防线」，按加固项处理，不单列缺陷。
- 没有验多平台差异（ARM64 / 国产系统），评审提的这条仍是空白。
