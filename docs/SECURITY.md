# 安全边界规范

四条边界：**路径 / 权限 / 敏感参数 / 执行隔离**。

这份文档写的是**规范**（要遵守什么）；`AGENTS.md` 的「十六个坑」记的是**案例**（已经踩过的坑）。
坑是事后复盘，规范是事前约束 —— 两者不重复、不矛盾，关系见[第 5 节](#5-与-agentsmd-十六个坑的互相引用)。

能自动查的那一半由门禁守住：

    bash tools/check_security.sh            # 全查；0 通过 / 1 有违规 / 2 用法错
    bash tools/check_security.sh --list     # 列出全部判据
    bash tools/check_security.sh --only path.write

每节最后一栏「机器判据」写明：哪几条门禁能查（**自动**），哪几条只能靠人看（**评审**）。

## 1. 路径边界

### 规则

1. **写入前，目标必须落在声明的根内。** 根用 `pwd -P` 解析（中间目录的符号链接也要解析）；
   目标的**每一级已存在目录**都要逐级检查 —— 哪一级不是真目录就停。
2. **不可信软链一律拒绝**：不跟随、不替换。**指向根之内**的软链同样拒绝 ——
   我们分不清它是不是用户故意放的（有人用软链共享配置），不做「看起来安全就放行」的判断。
3. **清单 / 配置里读出来的名字先过合法性校验**（不许 `/`、不许 `..`、不许空），
   再拼进路径。名字先变路径，`../` 就能把文件写到根之外。
4. **写文件走「临时文件 + rename」**：同目录落临时文件再 `mv` 过去。
   rename 是原子的 —— 失败要么什么都没发生，要么整体换新；而且它替换的是符号链接**本身**，
   不会顺着链接写到别处。

### 为什么

- 不校验根 ⇒ 名字里带 `../` 就能写到工程目录之外，而且**退出码是 0、日志里看不出来**。
- 跟随软链 ⇒ 内容写进链接指向的那个文件，链接本身纹丝不动，退出码还是 0 ——
  表现为「静默写到预期目录之外」。
- 直接 `cp -f` ⇒ 写到一半被打断（断电、磁盘满、进程被杀）留下的是**半截文件**，
  既不是旧内容也不是新内容；进程被杀掉还可能什么都不提示。

### 正例

```bash
root=$(cd "$project_dir" && pwd -P)

# 1. 名字先过合法性校验
if ! _sk_valid_name "$name"; then
  die 2 "invalid project name: $name"
fi

# 2. 目标必须在根内
target="$root/bin/$name"
if ! _sk_fs_in_dir "$root" "$target"; then
  die 3 "target escapes the project root"
fi

# 3. 路径里每一级已存在的目录都得是真目录（软链一律拒绝）
if ! _sk_fs_no_symlink_below "$root" "bin"; then
  die 3 "refusing to write through a symlink"
fi

# 4. 原子写：临时文件 + rename
fs_atomic_write "$target" "$content" 600
```

### 反例

```bash
# 反例 1：名字直接拼进路径 —— ../etc/passwd 就能写出根外
fs_atomic_write "$root/$name" "$content"

# 反例 2：先删再拷 —— 中途失败会留下半份库
rm -rf "$vendor_dir"
cp -R "$src" "$vendor_dir"

# 反例 3：目标已经是软链也照写 —— 内容会顺着链接落到别处
cp -f "$src" "$target"
```

### 机器判据

| 判据 | 类型 | 查什么 |
|---|---|---|
| `path.write` | 自动 | 写原语（`fs_atomic_write` / `fs_atomic_copy` / `fs_ensure_line` / `fs_ensure_block`）的调用点，所在函数必须带路径边界守卫 |
| `path.symlink` | 自动 | 行为判据：`_sk_fs_in_dir` 拦根外目标、`_sk_fs_rel_safe` 拦 `..`、`_sk_fs_no_symlink_below` 拦软链目录 |
| `path.name` | 自动 | 行为判据：`_sk_valid_name` 拒绝 `a/b` 与 `..`；且 `cmd_new` / `cmd_upgrade` / `cmd_demo` 必须调用它 |
| 根的选取 | 评审 | 根是不是「用户以为的那个目录」；跨设备的路径要不要单独处理 |
| 「不可信」的来源清单 | 评审 | 配置、命令行参数、环境变量、HTTP 响应 —— 哪些算不可信，枚举全不全 |

## 2. 权限边界

### 规则

1. **新建文件默认 600。** `fs_atomic_write` 的 MODE 默认值就是 `600`。
2. **覆盖既有文件时权限按显式口径走**：
   - `fs_atomic_copy`（搬文件）**保留目标原权限**；目标不存在时跟随源的权限。
   - `fs_atomic_write`（写内容）按传入的 MODE 落盘，**默认 600** —— 要保留原权限就显式传 MODE。
3. **秘密文件不进版本库**（`.env`、`*.pem`、`id_rsa`、`*.key`、`credentials*` …），
   **也不进日志**（文件名、路径、配置内容都可能带线索）。
4. 临时目录用 `mktemp -d`（自带 700），不要用 `mkdir` + `chmod` 补。

### 为什么

- 644 的秘密文件 = 同机任何用户可读。机器上不只有你。
- 覆盖时权限被「顺手改成 600」也不是好事：可执行文件会当场不可执行。
- 凭据进了版本库就等于公开了 —— git 历史删不掉。

### 正例

```bash
# 新建秘密文件：默认 600
fs_atomic_write "$conf_dir/token" "$token"

# 覆盖既有文件：保留它的权限（fs_atomic_copy 走这条）
fs_atomic_copy "$src" "$dst"

# 临时目录：mktemp 自带 700
workdir=$(mktemp -d)
trap_push 'rm -rf "$workdir"'
trap_install
```

### 反例

```bash
# 反例 1：新建秘密文件用了 644 —— 同机其他用户可读
fs_atomic_write "$conf_dir/token" "$token" 644

# 反例 2：秘密文件进了版本库
cp "$HOME/.ssh/id_rsa" "$project_dir/"
```

### 机器判据

| 判据 | 类型 | 查什么 |
|---|---|---|
| `perm.mode` | 自动 | 行为判据：`fs_atomic_write` 新建 600；`fs_atomic_copy` 覆盖保留原权限、新建跟随源 |
| `secret.tracked` | 自动 | 凭据文件不得出现在 `git ls-files` 里 |
| `.gitignore` 是否覆盖凭据文件名 | 评审 | 门禁只查「已经入库的」，忽略规则要人盯（见[第 6 节](#6-已有实现与规范之间的偏差)的偏差 3） |
| 哪些文件算秘密 | 评审 | 清单化；token / 证书 / 私钥 / 口令 / 备份文件 |
| 日志里出现路径与文件名 | 评审 | 路径里带用户名、token、账号名 |

## 3. 敏感参数

### 规则

1. **命令行里的口令 / 令牌必须显式声明脱敏**：
   - `run --secret-arg N` —— 第 N 个参数（**命令名不算**）必脱敏，可以写多次；
   - `run --redact-value V` —— 值等于 V 的地方一律脱敏（令牌夹在参数中间也遮得到）。
2. **启发式认不出的，由调用方显式标注。** 启发式只认得出「键名像敏感字段」
   （`--password`、`API_TOKEN=`、`Authorization:`、`-u` …），位置参数里的口令它认不出。
3. 环境变量 `SHELLKIT_SECRET_ARGS="2,3"` 对所有 `run` 生效（CI 里统一声明最省事）。
4. **不打印含凭据的命令行。** 直接调 `curl` / `ssh` 的路径不经 `run` 的脱敏 ——
   那条路只能靠「不打印」兜底。

### 为什么

日志里出现完整的命令行 = 把口令写进了日志文件，而日志常常比代码活得更久、传得更远
（采集系统、CI 输出、别人 `tail -f`）。

### 正例

```bash
# 正例 1：口令在第 2 个参数（命令名不算）
run --secret-arg 2 mysql -u app "$DB_PASSWORD"

# 正例 2：令牌夹在参数中间 —— 按值遮
run --redact-value "$TOKEN" curl -H "Authorization: Bearer $TOKEN" "$url"

# 正例 3：CI 里统一声明
export SHELLKIT_SECRET_ARGS="2,3"
```

### 反例

```bash
# 反例 1：位置参数里的口令没人声明 —— 日志里就是明文
run mysql -u app "$DB_PASSWORD"

# 反例 2：把口令拼进 URL —— 请求日志、代理日志、访问日志全都有
run curl "https://example.com/?token=$TOKEN"
```

### 机器判据

| 判据 | 类型 | 查什么 |
|---|---|---|
| `secret.redact` | 自动 | 行为判据：`run --secret-arg N` 真的遮住第 N 个参数；静态判据：调用点把敏感变量递给 `run` 时必须显式声明 |
| 哪些值算秘密 | 评审 | 口令、令牌、私钥、证书口令、会话 cookie |
| 脱敏后的日志是否还有线索 | 评审 | 长度、格式、拼接位置（`--user $name:$pass` 只遮一半） |
| `SHELLKIT_REDACT=0` | 评审 | 只能当调试开关，不能当配置项 |

## 4. 执行隔离

### 规则

1. **锁必须可回收。** pid 文件缺失 / 不可读时不是「合法的持有态」，
   按 `SHELLKIT_LOCK_STALE` 宽限期（未设置时 5 秒）之后**必须能回收** ——
   否则一次非正常退出就让这个锁名**永久不可用**，报错还说是「另一个实例在跑」。
   **活着的持有者绝不按年龄回收** —— 那等于把正在干活的进程的锁抢走。
2. **退出必收尾。** `trap_push` 注册清理动作，`trap_install` 才真正装上 trap；
   只注册不安装 = 退出时什么都不会收尾。注册不等于安装，库被 source 时不该悄悄接管别人的 trap。
3. **并发实例互相隔离。** `run_concurrent` / `parallel_map` 的每个实例，
   stdout / stderr / 退出码各写各的临时文件；实例之间不共享工作目录与状态文件。
4. 拿到锁就入清理栈（`lock_acquire` 成功即注册退出时释放），忘记 `lock_release` 也不会留下死锁。

### 为什么

- 永久不可用的锁：用户只能去查一个**不存在的进程**，报错还指向错误的方向。
- 只注册不安装：脚本被 `kill` 或断电时留下半成品目录、临时文件、跑了一半的部署。
- 并发实例共享输出文件：输出互相覆盖，日志对不上是谁干的。

### 正例

```bash
# 正例 1：拿不到锁就退出（3 = 前置条件不满足）
lock_acquire deploy 30 || exit $?

# 正例 2：注册清理动作后必须装上 trap
trap_push 'rm -rf "$workdir"'
trap_install

# 正例 3：并发跑 N 份；stdout 只给成功数，stderr 逐实例标注
run_concurrent 8 -- ./deploy.sh "$target"
```

### 反例

```bash
# 反例 1：注册了清理却没装 trap —— 退出时什么都不会收尾
trap_push 'rm -rf "$workdir"'

# 反例 2：拿不到锁就往下跑 —— 两个实例同时改同一个目录
lock_acquire deploy 30
./deploy.sh
```

### 机器判据

| 判据 | 类型 | 查什么 |
|---|---|---|
| `exec.lock` | 自动 | 行为判据：pid 缺失且过了宽限期就能回收；持有者还活着绝不回收；宽限期内不回收 |
| `exec.trap` | 自动 | 调用了 `trap_push` 的文件必须调用 `trap_install` |
| `exec.atomic` | 自动 | 行为判据：`fs_atomic_copy` 不顺着软链写穿；结构判据：写原语走「临时文件 + rename」 |
| `exec.concurrent` | 自动 | `run_concurrent` 的每个实例输出各写各的文件 |
| 锁名是否够具体 | 评审 | 锁名粒度（一个部署一个锁，还是一台机器一个锁） |
| 临界区大小 | 评审 | 锁的范围是不是覆盖了全部会冲突的写操作 |

## 6. 已有实现与规范之间的偏差

规范写的是**该守的**，实现是**现在这样**。两者不一致的地方，如实记在这里 ——
不粉饰，也不假装已经改好了。

| # | 偏差 | 现状 | 影响 |
|---|---|---|---|
| 1 | `fs_atomic_write` 覆盖既有文件**不保留**原权限 | 实现按传入的 MODE 落盘（默认 600）；但函数上方的 `@exitcode` 注释写的是「原文件权限保留」 | 注释与实现不符；保留原权限的是 `fs_atomic_copy`。**注释要改** |
| 2 | `_sk_fs_rel_safe` / `_sk_fs_in_dir` 在库内**没有调用点** | 公共内部实现已就位（`lib/core/fs.sh`），CLI 侧用的是同判据的私有版本 `_sk_upgrade_rel_safe` / `_sk_upgrade_in_dir` | 库用户应优先用这两个公共版本；CLI 与库之间有一份重复实现 |
| 3 | `.gitignore` 没有覆盖凭据文件名 | 只覆盖 `.upstream/`、*.mo.bak`、`locale/**/*.mo~`、`site/node_modules/`、`.DOCS.*` | `.env` / `*.pem` / `id_rsa` 一旦被 `git add` 就入库了。门禁只查「已入库的」，**忽略规则要补** |
| 4 | `fs_backup` 用 `cp -p` 直接备份，不是原子写 | 备份是「留一份旧的」，不参与覆盖语义 | 中断可能留下半截备份文件；影响面小，但要知情 |
| 5 | `shellkit` 自己的安装与 vendor 暂存用 `cp -f` | 落在暂存目录里，随后整体换目录（坑 11 的做法） | 暂存目录内的单文件写不是原子的；整体换目录兜底 |
| 6 | 所有权清单里的相对路径，拼进目标路径前**没有**再过 `_sk_fs_rel_safe` | `shellkit` 的 `_sk_skill_uninstall_from` / `_sk_skill_list` 直接用清单里的相对路径拼路径 | 清单是磁盘上的文件、用户可改：清单里写 `../../x` 就能让卸载删到根外。**要补校验** |
| 7 | `lib/core/http.sh` 直接调 `curl`，不经 `run` | 因此**不经过 `run` 的脱敏**；现在靠「不打印命令行」兜底 | 一旦有人把 curl 的命令行打进日志，令牌就出去了 |

## 7. 门禁能查什么、不能查什么

门禁：`tools/check_security.sh`（10 条判据，行为判据 6 条 + 结构判据 4 条）。
自证：`tests/test_security.sh` 对每条判据都做一次「注入违规 → 门禁红」。

门禁查不了的（只能靠评审）：根的选取是否恰当、哪些值算秘密、哪些文件算秘密、
锁的粒度与临界区、并发实例之间共享的状态、日志链路本身的泄漏。
