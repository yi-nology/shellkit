# shellkit 0.3 —— 易用性：让人和 AI 都能快速用起来

前置：docs/superpowers/specs/2026-11-08-shellkit-0.2-evolution-design.md（0.2.0 基线）

## 0. 要解决的问题

0.2.0 的能力已经够用，但**用户不知道怎么用**：

1. README 讲「库有什么」，没讲「我要做 X 该抄哪段」。模块表按加载顺序排，不是按任务排。
2. 三份文档（README / MIGRATING / REFERENCE）没有「你是哪种读者」的导航。
3. 仓库根没有 AGENTS.md。AI 进来只能读给人看的 README。
4. `shellkit new` 生成的工程里没有给 AI 的说明 —— 而 AI 真正写脚本的地方是**那些工程**。
5. AI 写 Bash 的失败模式高度集中：拿 Bash 4 语法写 3.2 库（关联数组、`${v^^}`、
   `local -n`、`mapfile`）。库里没有一处把「别写什么 → 写什么 → 在 3.2 上会怎样」摆出来。
6. 文档会悄悄过期：函数改名、示例跑不通，没人发现。

## 1. 一份真相源，三个产物

给 AI 的硬事实只写一遍，放 `docs/ai/`：

    docs/ai/contract.md      # 硬规则 + 禁用语法对照 + 自检命令 + 查证纪律
    docs/ai/repo.head.md     # 前置：本仓库特有的一节
    docs/ai/project.head.md  # 前置：生成工程特有的一节
    docs/ai/skill.head.md    # 前置：任意项目里引入的一节

产物 = head + contract，由 `shellkit docs` 拼装：

| 产物 | 读者 | 什么时候读 |
|---|---|---|
| `AGENTS.md` | 来改 shellkit 本身的 AI | 改库、加模块、修 bug |
| `templates/AGENTS.md` → 落到新工程 | 在用户自己工程里写脚本的 AI | 加子命令、改配置、跑测试 |
| `skills/shellkit/SKILL.md` | 想在任意项目用 shellkit 的 AI | 引入库、写第一个脚本 |

三条约束：

- 三份产物**都是生成物**，头部写明「请勿手改」。改内容改 `docs/ai/`，再跑 `shellkit docs`。
- `shellkit docs --check` 比对全部四份（含 REFERENCE.md），不一致返回 SK_VERIFY(5)。
- 拼装由 `tools/ai_doc.sh` 做（printf + cat，不引入依赖）。

## 2. contract 的骨架

    # 你在用 shellkit 写 Bash
    ## 三条硬事实
    Bash 3.2 基线 / stdout 只给数据 / 出参用 printf -v
    ## 禁用语法对照（表：别写什么 | 写这个 | 3.2 上会怎样）
    ## 拿到任务先做三件事
    1. 需要的能力先在 lib/core/*.sh 里找，别自己写一遍
    2. 不确定函数签名就查 docs/REFERENCE.md，不要发明函数名
    3. 写完跑本场景的验证命令
    ## 交付前自检
    ## 常见任务的落点（表：我想到的事 -> 用哪个函数）

「不要发明函数名」是重点：AI 用库最大的坑不是语法，是幻觉出 `conf_require` 这种不存在的 API。

## 3. 人类侧

### 3.1 docs/COOKBOOK.md

按「我要做 X」组织，每节三段：场景 / 可直接抄的代码 / 为什么这么写。首批 14 个：

配置读写与优先级、下载并校验（含镜像回退）、等端口与等 HTTP、单实例并发、
幂等改配置文件、装成 systemd 服务、加一个子命令、非交互与超时、
失败即停与清理栈、重试、原子写、彩色与非彩色、i18n、写测试。

### 3.2 examples/

两个**真实工程**，不是骨架，各自 `make test` 绿：

- `examples/deploy-service/`：单实例锁 + 幂等写 systemd 单元 + 等端口 + 清理栈 + 子命令
- `examples/fetch-release/`：下载带镜像回退 + sha256 校验 + 解包 + 原子替换

不 vendor 库，用相对路径加载；README 写清「拿走时先 `shellkit vendor .` 再改那一行」。
理由：仓库里不该躺第二份库副本（会漂移），而 examples 的价值是展示写法，不是开箱即用。

## 4. 文档门禁

`tools/check_docs.sh`（零依赖，bash + awk）：

1. 所有 markdown 里带 bash 标记的代码块必须 `bash -n` 通过 —— 即片段必须语法自洽；
   只想示意的用 text 标记。
2. 块内「命令位置」的标识符必须满足以下之一，否则判红：
   - 在 `docs/REFERENCE.md` 的公开函数集合里
   - 在同一个块内用 `name()` 定义过
   - 在 `tools/check_docs.allow` 白名单里（内建命令、演示用的外部命令）
3. 拼装产物与源一致（由 `shellkit docs --check` 负责）。

价值：函数改名后，文档里所有旧名字立刻变红；AI 幻觉出来的 API 抄进文档也会红。

## 5. 截图：真实输出渲染成 SVG

`tools/term_shot.py` 按 `.shot` 文件执行真实命令，把「提示符 + 命令 + 真实输出」
渲染成终端窗口样式的 SVG（矢量、可 diff、无隐私、不会过期）。

    docs/shots/doctor.shot        -> docs/shots/doctor.svg
    docs/shots/new-project.shot   -> docs/shots/new-project.svg

- 只有 python3 可用时才生成；缺失时 `make shots` 打 warn 跳过，不阻断 `make check`。
- `make shots` 生成，`--check` 模式比对内容（真实输出变了就红）。

## 6. README 重写口径

- **不提「参考 / 取经自哪个项目」**。只讲 shellkit 怎么做、为什么这么做。
- 顶部放「你是哪种读者 → 看哪份」导航。
- 用 SVG 截图替代大段描述（doctor 输出、new 一个工程、测试全绿）。
- 保留五条硬约定与退出码表（它们是契约，不是营销）。

## 7. 不做

- 不做 llms.txt（与 AGENTS.md 重复，多一份会漂移的产物）。
- 不做 shell 补全、不多模板（仍不在本轮）。
- 不接 asciinema / svg-term 等外部录制工具（会引入运行时依赖）。
- 不改任何既有函数的语义；0.3.0 只加不改。

## 8. 验收

1. `make check` 绿，含新增的 check-docs 与 docs-check。
2. `./shellkit docs --check` 四份产物全部最新。
3. `bash tools/check_docs.sh` 通过；故意把文档里某个函数名改错 -> 必须判红。
4. `examples/deploy-service` 与 `examples/fetch-release` 各自 `make test` 绿。
5. `make shots` 的 SVG 来自真实执行；改一行输出后重新生成，diff 非空。
6. `shellkit new` 出来的工程里有 AGENTS.md，且 `make test` 当场通过。
7. README 里不再出现「参考 / 取经 / 类似 bashly」这类表述。
8. bash 3.2 与 CI ubuntu 双绿。
